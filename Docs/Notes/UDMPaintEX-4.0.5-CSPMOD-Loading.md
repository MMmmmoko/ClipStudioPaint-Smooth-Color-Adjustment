# UDMPaint EX 4.0.5 装载 CSPMOD 的调查

调查对象为安装目录中的 `UDMPaintEX.exe`，文件版本 4.0.5.0，产品版本 4.0.5，SHA-256 为 `A7ADD7FCAA5FD51387974A0DE882B699586224E8141C961354DBFCE1FE87F9A9`。同目录的 `CSPMOD.dll` 与 CSPMOD Release 构建哈希一致。

## 运行证据

- 2026-11-13 02:12 的建表日志记载同一宿主生成了 41 项地址，证明此前进入过 CSPMOD 初始化。日志里的插件特征缺失没有中止建表。
- 02:20 启动的主进程在 Windows 应用事件日志中多次报告同一个访问冲突。报告的故障模块来自 UDM 安装目录，为 `MSVCP140.dll` 14.29.30139.0。
- 主窗口出现后，主进程加载了同一 `PlugIn\PAINT` 目录下的 15 个滤镜或导入导出模块。CSPMOD 以及负责加载它的 `AALoad.dll`、`SmoothFilter_GaussBlur.dll` 和 `SmoothFilter_MotionBlur.dll` 均未留在主进程的模块列表。帮助菜单入口、面板状态、缩时摄影和曲线更新的函数入口与磁盘原始字节一致。

## 运行库复现

当前 CSPMOD 使用 MSVC 14.44 构建，导入 `_Mtx_lock` 和 `_Mtx_unlock`。UDM 自带 14.29 运行库能够解析这些导入，但它的互斥锁实现从内部对象读取虚表指针，依赖旧版运行库的初始化行为。用相同的 14.44 工具集创建默认 `std::mutex`，再交给 UDM 安装目录运行库的 `_Mtx_lock`，独立测试得到与事件日志完全一致的 `0xC0000005` 及同一故障指令。先使用旧运行库自己的 `_Mtx_init_in_situ` 初始化时成功。系统目录的 14.51.36247.0 运行库也能直接处理 14.44 的默认构造。

故障位置可由 14.29.30139.0 的导出 `_Mtx_lock` 追到内部加锁实现，再匹配取出互斥对象内部指针并继续解引用的分支。复现依据为异常发生在同一条指令。当前事件日志未提供调用栈，崩溃报告正文受权限限制，故未确认最先触发该互斥锁的是哪一项初始化。

## 对照可用版本和构建配置

可正常运行的 `CSPMOD_c5_0_0_m2_2_3_beta` 同样使用 14.44 链接器，并额外导入 `_Mtx_init_in_situ`。故障构建的 CSPMOD 编译命令未定义 `_DISABLE_CONSTEXPR_MUTEX_CONSTRUCTOR`。用相同编译器和 `/MD` 分别构建两个最小 DLL，在同一份 UDM 14.29 运行库中验证。未定义宏的构建发生 `0xC0000005`，定义宏的构建正常完成加锁和解锁。

指定的 `nim_duilib-main/duilib/duilib.vcxproj` 在 x64 Release 中定义 `_DISABLE_CONSTEXPR_MUTEX_CONSTRUCTOR=1`，实际编译日志也含该选项。项目的 Release 输出为 `nim_duilib-main/lib/x64/duilib.lib`。最近一次故障构建通过命令行指定该库目录。其头文件原本经 `Common/include/duilib` 目录联接指向同一份源码。未指定参数时，旧项目配置会从 `Common/bin` 选另一份同名库。

CSPMOD 项目现在默认从同一个 `nim_duilib-main` 根目录引用头文件和显式库文件，并采用兼容互斥锁初始化。UDM 的运行库保留原版本。修复 DLL 装载后，用户确认旧功能恢复。此前按宿主文件名跳过的三个新功能，现均进入同一套定位流程。

Release x64 在未传入库目录覆盖参数时成功构建。55 个当前源文件的编译命令均含兼容宏，链接日志和头文件依赖日志都指向指定 duilib 项目，新 DLL 导入 `_Mtx_init_in_situ`。在 UDM 4.0.5 原目录重启后，确认主进程同时装载了新版 CSPMOD 和原有 14.29 运行库。帮助菜单、面板状态和缩时摄影入口均已跳转到新版 CSPMOD。检查时该进程尚无新的应用程序崩溃事件。

UDM 的命令标签编号与 CSP 样本存在差异。UDM 里沿用 CSP 自由变换的标签编号会命中缩放旋转命令，因此以 `transformfree` 的目录项确认入口，再用拖动和采样代码选择布局。

地址表架构更新为 25。UDM 4.0.5 原目录中的建表日志在重建后由两轮旧记录变为一轮，生成 140 项。现有插件匹配缺失仍记录为错误。无法验证的功能会记录失败的特征，依赖它且尚未检查的项目会记录为跳过。

用内存中的样本模拟定位特征缺失和歧义，确认自由变换整组回退，色阶及自定义调整图层拒绝无效入口。三份原始文件均通过定位器测试。已在 UDM 4.0.5 进程中只读确认新版 DLL 装载，以及自由变换、两条色阶回调、调整图层工厂和命令栏入口跳转到新版 DLL。

UDM 4.0.5 手动确认普通色阶、色阶调整图层，以及从原生菜单新建、预览和双击编辑试验反相均正常。首轮自由变换拖动时严重卡顿并出现 CPU 占用高峰。排查期间，较早布局曾采用 33 毫秒最短提交间隔和刷新完成后 8 毫秒的额外等待。现两套布局均合并拖动脏区，并以相邻两次提交开始时间至少间隔 16 毫秒为准。鼠标释放时由原生路径提交最终预览。可选诊断记录每次拖动的刷新、四边形采样入口、GPU 批次、回退的图块及刷新耗时。

旋转手柄通过基础拖动中的旋转动作匹配。两套布局均用动作 `4` 进入旋转计算，随后由与其他拖动共用的脏区回调提交。用户在 UDM 中确认松手前画面随旋转更新。

Ctrl 拖角的诊断在 4.70 秒内记录 53 次刷新请求、1,060 次四边形入口和 1,054 次 CPU 图块回退。采样器读取三个有效颜色通道，目标颜色平面每像素占四字节，透明度使用独立平面。旧检查要求有效通道数等于目标存储宽度。修正后的 GPU 路径分别使用原生源平面和目标平面的步长，并沿两条原生插值内核验证目标写入循环只写有效颜色通道。三个有效通道时保留目标的第四字节。

硬件 D3D11 测试覆盖 4 字节颜色和 3 通道带填充字节两种图块，验证颜色和透明度写回，以及后一种布局的填充字节保留。UDM 中用户确认采样修正后整体正常。在仍采用 33 毫秒间隔的测试中，一段 7.92 秒的 Ctrl 拖动记录了 135 次刷新请求及 2,700 次可加速的四边形采样，其中 2,470 次使用 GPU。剩余 230 次因无法确定可用的源采样区域而沿用原生处理。
